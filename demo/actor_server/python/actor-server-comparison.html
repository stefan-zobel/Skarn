Benchmark report · Concurrency

The same actor web server in Skarn and five ways in Python

One acceptor, N workers, each connection handed to a free worker. In Skarn with actors, in Python 3.14 with threads (with and without the GIL), subinterpreters, processes and prefork. All of them are driven by the same load generator, in one run, and every answer is checked.

Laptop · 6 cores / 12 threads Windows · CPython 3.14.7, GIL and free-threading builds 16 clients · 5 rounds · medians 330 load runs · 0 failures
Summary
  • Skarn is ahead or level on every absolute measure, behind on none: throughput, latency, time per request, start time, memory.
  • For CPU-bound requests Skarn serves 2.0 to 2.7 times as many as the best Python contender at every worker count, with a lower p50 and p99. That is mostly the interpreter: one unit of work takes CPython 2.3 times as long.
  • For pure I/O prefork draws level at four and six workers (±2.3 %). Elsewhere Skarn leads by 7 to 10 %.
  • Scaling is where Python comes closest: subinterpreters reach 4.7× and free-threaded threads 4.4× on twelve workers, Skarn 5.4×. Threads with the GIL do not scale at all.
  • Isolation is expensive in Python: twelve subinterpreters take 67 MB and 281 ms to the first answer, twelve Skarn actors 6 MB and 44 ms. Free-threading is cheap (15.5 MB, 76 ms), but its threads share memory.

Part 1 · CPU-bound

/work/8000: each request computes for about 1 ms (Skarn) or 2 ms (Python)

The digit sum of all numbers from 1 to 8000, the same loop statement for statement in both languages. More workers can compute more at once, provided the model allows real parallelism.

Throughput by worker count

Latency per request, as the client sees it

Bar to p50, line to p99, mark at p95. 16 clients wait at the same time, so the latency includes the time spent in the queue. With one worker, that is 16 requests one after another.

  • Threads with the GIL stay at 1.0× at every worker count, and their p99 grows with more threads (39 → 49 ms). The GIL lets only one thread run Python code at a time. This is where classic Python is really weak.
  • Without the GIL the same code scales 4.4×. The subinterpreters scale best of the Python contenders (4.7×) and stayed 7 to 15 % ahead of free-threading in every round. Processes and prefork reach 4.3×.
  • Up to six workers the subinterpreters scale as well as Skarn (3.3× against 3.1× at four); at twelve Skarn pulls ahead. The factor flatters the slower interpreter, though: accepting and handing over cost both about the same, and next to work that takes twice as long it weighs less.
  • In absolute terms Skarn is 2.0 to 2.7× ahead. At twelve workers its p99 (4.7 ms) is below every Python contender's median.

Part 2 · Pure I/O

/: accept, read a line, answer, close

Almost nothing is computed here. The bottleneck is the connections themselves, the hand-off to the worker, and the load generator running on the same machine. More workers therefore help little.

Throughput by worker count

Latency per request, as the client sees it

Bar to p50, line to p99, mark at p95.

  • For I/O Python is not weak. Prefork, where every process accepts connections itself (as gunicorn does), is level with Skarn at four and six workers, at about 20,000 requests/s.
  • Free-threading is the best Python contender with one worker (15,700 against Skarn's 16,700): the acceptor and the worker do not take turns. At four workers one slow round (10,800) pulls its median down.
  • Threads with the GIL keep up but stay between 12,300 and 14,100. Handing each connection to another process halves the throughput (procs).

Part 3 · Time per request

What a single request costs

With one worker that is busy all the time, 1 / throughput is the time a request occupies it, from accepting to closing. Next to it is the pure computing time of work(8000) on one thread, without HTTP.

CPU-bound request (/work/8000), one worker

The lighter part shows the pure computing time: Skarn 0.83 ms, CPython 1.90 ms, free-threaded 1.98 ms. The rest is HTTP and hand-off: about 0.25 ms for Skarn and 0.4 to 0.6 ms for Python.

I/O request (/), one worker

There is no work here. This is what accepting, handing over, reading, answering and closing cost. The hand-off to another process costs the most.

Part 4 · The price of isolation

Start time and memory

This is where the cost of each model itself shows, independent of interpreter speed. A Skarn actor is a thread with its own heap over a shared program image. A Python thread shares everything; a subinterpreter loads its modules itself, a process loads everything.

Start to first answer

Median of ten starts. Skarn compiles from source at start. From a precompiled .skbc image it takes 12 ms.

Private memory, 12 workers, under load

Private pages, each counted once. The pale extension shows the RSS: for processes it counts the same libraries several times and rises to 211 MB.

  • A subinterpreter costs about 5 MB and 17 ms. Twelve take 67 MB and 0.28 s to the first answer, because, as in Skarn, all workers are created before the first accept. Twelve Skarn actors cost 6 MB and 44 ms.
  • Processes are heavier still: 122 MB private, just over 0.2 s.
  • Threads are cheap, with or without the GIL: 76 to 80 ms and 11 to 16 MB. Without the GIL they also compute in parallel, and that makes free-threading Python's best balance.
  • What free-threading costs is safety, not speed. Its threads can change the same object at the same time, and guarding that is the programmer's job. Skarn's actors share nothing: a message is copied, and the checker keeps what cannot be copied out of messages.
Method

Why the comparison is fair

Python may look bad where it is really weak, but not because of the way it was measured. Every Python variant therefore got its best mechanism from the standard library.

  • The same client for everyone. The load generator checks every answer, and for /work the exact value (work 8000 = 136008). So both sides provably compute the same thing.
  • The same architecture. One acceptor, N workers, one request per connection. Free workers report to the acceptor, and it hands a connection only to a worker that has reported.
  • Free-threading on the same code. Both threads contenders run the very same server. One runs on the GIL build of CPython 3.14.7, the other on the official free-threading build of the same version (python-freethreaded). The script checks that the GIL is really off at run time.
  • No queue that polls. concurrent.interpreters.Queue.get() sleeps 10 ms whenever the queue is empty. That would have stalled every subinterpreter worker after every connection. The subinterpreters therefore talk over a local socket pair, which blocks in the operating system.
  • The fastest hand-off: socket.share() between processes, not the slower pickling path.
  • Prefork as a variant of its own, for the fair objection that a Python server would not pass sockets between processes.
  • The same start. Every server announces its port right after listen and accepts at once. Only then does the first request go out. Otherwise, on Windows, a connect to a port that is not yet listening costs about 0.5 s.
  • One run, rotating order, medians. All six contenders were measured in the same run. Every run starts with a short warm-up, the order of the contenders changes in each of the five rounds, and memory is measured in runs of its own, so sampling it does not slow the throughput runs.
  • Interpreter speed and scaling kept apart. The speed-up relates each contender to its own 1-worker value, and work(8000) is timed alone on one thread.

The machine slows down under sustained load

At twelve workers every contender lost a quarter or more of its rate from the first round to the last (Skarn 5,495 → 3,959, subinterpreters 2,090 → 1,446), most likely thermal throttling. The ratios stayed put: Skarn served 2.8 to 3.0 times as many requests as free-threaded Python in every single round. Absolute numbers on this laptop are good to about ±15 %; the comparisons within the run are what the rotating order protects.

Not measured

  • asyncio: a single thread, like Skarn's std::poll loop, so not a comparison of actor models.
  • Other operating systems: all numbers are from Windows.
The load generator runs on the same machine and shares the cores with the server; that holds for every contender alike.
